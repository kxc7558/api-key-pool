# 设计文档 — API Key 调度与协议转换

## 为什么不用现成的

| 工具 | 短板 |
|---|---|
| LiteLLM | 支持 OpenAI 协议，不支持 Anthropic Messages 协议，调度策略不透明 |
| new-api | 主打协议转换，调度逻辑是黑盒，无法精确控制冷却/退避参数 |
| 单 Key 直连 | 没有额度共享、限流容灾、多 Key 轮询分摊 |

自研的好处：**调度策略完全可控**，每个参数（冷却时间、探活间隔、排队预算、连坐范围）都能精确定义，踩坑时知道哪一层出了问题。

## Key 生命周期状态机

```
                    ┌─────────────────────────────────────┐
                    │         ACTIVE（正常服务）            │
                    └──────┬──────────────────────────────┘
                           │
           429 / 401 / 403 │
                           ▼
              ┌────────────────────────┐
              │  判定 429 类型          │
              └──┬──────────────────┬──┘
                 │                  │
     瞬时速率限制 │                  │ 持续额度用尽
    （秒级恢复）   │                  │ （≥15min 持续）
                 ▼                  ▼
    ┌─────────────────────┐  ┌─────────────────────┐
    │ 指数退避冷却          │  │ 额度冻结             │
    │ 60s→2m→4m→…→10m    │  │ cooldownResetMs     │
    └──────────┬──────────┘  └──────────┬──────────┘
               │ 冷却到期                │ 冷却到期
               ▼                         ▼
        ┌─────────────────────────────────────┐
        │  HALF_OPEN（半开探活）               │
        │  用 GET /models 验证，免费不占额度     │
        └────┬────────────────────────┬───────┘
             │ 探活成功               │ 探活失败
             ▼                        ▼
        ACTIVE（回池）           再试（最多 3 次）
                                       │ 连续 3 次失败
                                       ▼
                                 回池（避免永远冻住）
```

**关键设计决策：429 分两种**

`429` 有两种完全不同的含义，处理方式截然不同：

| 类型 | 特征 | 处理 |
|---|---|---|
| 瞬时速率限制 | 单次数次 429，秒级即恢复（商汤 TPM 限制） | 指数退避冷却，**不冻结** |
| 持续额度用尽 | 连续 ≥N 次 429 **且**持续 ≥N 分钟（商汤 `tpm exhausted`） | 冻结 `cooldownResetMs`（商汤配 5h） |

只数次数必然误判——这是 2026-09-16 修复的核心 bug（全池误冻结），当时把「5h 500 次的长期平均」当成了「每分钟瞬时上限」，导致正常连续对话就触发全池冷却。

## 连坐冷却与账号分组

**问题**：英伟达 40 RPM 是按**账号**算的，同账号多 Key 不叠加额度。

**设计**：
- `config.json` 里 `accounts` 字段定义账号分组
- 同账号内的所有 Key 共享 `rpmPerAccount` 限流计数
- 一个 Key 触发 429 → 整组进入冷却（**连坐**）
- 组内恢复时，所有 Key 一起回池

**参数**（商汤组实测配置）：
```
商汤组 25 Key（分 3 账号：8/8/9）
rpmPerAccount = 10   （500次/5h ≈ 0.17 RPM，本地只做粗保护，实际由上游限流管）
maxConcurrencyPerKey = 3
```

> `rpmPerAccount=10` 是 2026-09-16 修复后的值，从 3 提高到 10——让上游真实限流来管，本地只做粗粒度保护。

## 半开探活（Half-Open Probe）

**为什么不用 `POST /chat/completions` 探活**：
- 消耗真实额度
- 返回延迟不稳定（英伟达冷启动 56~113s）

**为什么用 `GET /models`**：
- 免费，不占额度
- 响应快（<2s）
- 平台普遍支持（ModelScope/商汤/OpenRouter 均实测通过）
- 英伟达例外：`/v1/models` 完全不可达（60s 超时），该平台须手填模型名

**探活失败处理**：
- 连续失败 3 次即放回池（防止探活端点慢的平台把 Key 永久冻住）
- 可配 `probeTimeoutMs`（英伟达需要 180s+）

## 排队快速失败与降级兜底

**排队预算**（`waitForSlotMs`，默认 3000ms）：

```
所有 Key 不可用
  → 计算 minWaitMs（最早恢复时刻 - 现在）
  → minWaitMs ≤ 排队预算？
      是 → 精准 sleep 到恢复时刻，再继续
      否 → 立即 503 + retry-after（不白等）
  → 若等待超过预算的一半还等不到 → 自动降级到 fallback 候选（如 pro → 英伟达）
```

这个设计来自 one-api 的 `ignoreFirstPriority`：主力排队太久时，自动降到兜底 Key，不傻等。

## 双协议转换（OpenAI ⇄ Anthropic）

**设计原则：转换只在边界发生，中间复用同一条调度链路。**

```
Anthropic 客户端（Claude Code）
  → POST /v1/messages
  → anthropic.js: toOpenAI()       （协议入口）
  → handleChat()                    （轮询/429换Key/冷却/熔断/排队，全复用）
  → anthropic.js: jsonToAnthropic() / createStreamTranslator()
  ← Anthropic 客户端
```

**关键协议差异处理**（`anthropic.js`，纯函数，不碰网络/Key）：

| Anthropic 概念 | OpenAI 映射 | 注意点 |
|---|---|---|
| `user` 消息含 `tool_result` | 拆成 `role:tool` 消息 + `user` 文本 | 顺序：tool 在前，user 在后 |
| OpenAI `tool_calls` 分片 | `content_block_start(tool_use)` + `input_json_delta` 序列 | 流式累积，非单条 |
| 上游 `reasoning_content` | **丢弃** | thinking 块需签名，回放不了，且客户端会狂跳 Thinking |
| OpenAI 流式不给 `input_tokens` | 优先用上游真实 usage，没有就本地估算 | **必须非零**——填 0 会让客户端以为上下文没占用、永不自动压缩 |
| `x-api-key` 头 | **显式挡掉，不透传** | 否则把分发 Key 泄给上游平台（安全洞，2026-09-18 修复） |

**测试覆盖**：`tests/verify-anthropic.js` 61 项（协议转换单测 + 流式事件序列 + 老路径回归）。

## 用户配额落盘

**问题**：分发用户的 `dailyCount/totalCalls/lastCallAt` 此前纯内存态，服务重启即清零，配额可被绕过，面板读数不可信。

**设计**：`usage-state.json`（已 gitignore）

- 记账后 3 秒节流落盘 + 每分钟兜底 + `SIGINT/SIGTERM` 保存
- **首次启动才加载**（热重载时跳过，避免磁盘旧值覆盖内存最新计数）
- 实测：调用 3 次 → 重启 → 仍是 3 次 ✅

## 已知限制

- 英伟达 `/v1/models` 完全不可达，该平台必须手填模型名
- OpenRouter free 模型不支持工具调用（只把 JSON 写正文）
- 商汤 `max_tokens < 1024` 时思考过程吃光额度、正文为空（客户端侧问题，非池子 bug）
- 开机自启：启动文件夹快捷方式 `TargetPath` 为空（根因已定位，未修）
